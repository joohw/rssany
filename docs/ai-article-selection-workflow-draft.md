# AI 技术文章选题筛选与交付规范（结构优化稿）

## 1. 任务定义

### 1.1 任务目标

从用户维护的技术博客 RSS、公司与实验室研究博客、研究者个人博客、技术平台及 `awesome-frontier-blogs` 目录中，筛选近期值得整数智能和 ZODA 编译、转载或深度解读的 AI 技术文章。

核心交付价值不是简单翻译技术博客，而是回答：

> 这篇文章为什么值得整数智能和 ZODA 分享？它揭示了哪些具体的数据、评测、环境、轨迹、Judge、Harness、验证、成本或能力归因问题？

### 1.2 默认交付参数

- 时间窗口：最近 30 天，以北京时间解释。
- 交付数量：10–15 篇，通常以 12 篇为目标。
- 主题配比：至少 60% 直接属于 Eval、Benchmark、Data、Judge、Harness、Agent 评测或评测基础设施。
- 团队准入：正式候选仅限 T1/T2。
- 质量原则：有效文章不足时宁缺毋滥，不为满足数量降低标准。
- 重复推荐：允许再次推荐，但必须标注此前推荐日期。
- 竞品来源：METR、LangChain 默认仅用于竞品监测；除非用户明确要求，否则不进入常规推荐。

### 1.3 信源边界

允许采集：

- 公司研究博客；
- 大学、研究院和实验室博客；
- 研究者个人博客；
- 技术平台；
- `awesome-frontier-blogs`；
- Hacker News 和 Newsletter，但二者只能作为线索入口。

限制如下：

- X/Twitter 不作为候选文章的原始来源。
- 目录站、Hacker News 和 Newsletter 只能用于发现；最终事实与链接必须回到原始文章。
- 微信公众号和小红书不在本 Skill 范围内。

## 2. 执行准备

### 2.1 必读规则文件

执行前按顺序读取：

1. `source-registry.json`：允许使用的信源；
2. `selection-and-output.md`：硬门槛、预分层与交付格式；
3. `scoring-and-recommendation.md`：内容价值判断；
4. `scoring-execution.md`：T/P、分数、等级与准入口径；
5. `propagation-validation.md`：传播验证规则。

### 2.2 环境检查

确认以下条件：

- Node.js 20–23；
- RSSAny 0.5.1；
- 129 个注册信源；
- RSSAny adapters 可用；
- RSS、网页源和目录源的抓取状态正常。

首次使用或信源发生变化时运行：

```bash
node scripts/install.mjs
node scripts/sync-rssany.mjs --dry-run
node scripts/sync-rssany.mjs --apply
```

配置同步必须满足：

- 只增不删；
- 修改前备份；
- 不覆盖其他信源和用户配置；
- 重复运行不产生重复项；
- 不自动安装 Node.js 或 RSSAny；
- 不因端口占用终止未知进程。

### 2.3 降级策略

RSSAny 不可用时，可以降级读取公开 Feed、目录原始数据和 Skill 自带网页适配器，但必须明确说明动态网页等无法覆盖的范围。

## 3. 选题漏斗

整个流程分为五层。每一层都必须记录进入数量、退出数量和淘汰原因。

### 3.1 第一层：采集原始条目

运行：

```bash
node scripts/collect-candidates.mjs --days 30 --target 12 --refresh
```

记录：

- 实际抓取成功的原始条目数；
- 采集来源；
- 缓存状态；
- 失败信源和不可覆盖范围。

### 3.2 第二层：清洗、去重与硬门槛

先执行：

- URL 规范化；
- 删除 GPT/ChatGPT 归因参数；
- 合并 RSS、目录和论坛产生的重复条目；
- 检查发布时间和正文访问状态；
- 匹配历史推荐记录。

候选必须同时满足：

- 精确发布时间在时间窗口内；
- 原始文章可访问；
- 正文具有足够技术内容；
- 至少包含任务、方法、数据、实验、指标、案例或系统设计中的一项；
- 能形成具体的数据或评测切入角度；
- 不是匿名传言或纯目录摘要。

直接淘汰：

- 纯产品宣传；
- 融资和人事稿；
- 活动报名；
- 无录像 Webinar；
- 短 Release Note；
- 无技术正文的发布摘要；
- 无法核验精确日期的文章；
- 只能宽泛讨论行业影响、无法形成专业判断的内容。

arXiv 文章还必须核验论文 affiliation。只推荐能够确认来自顶级研究机构、大型科技公司研究团队或合格一手团队的成果；署名或机构层级不清时从严淘汰。

### 3.3 第三层：T/P 预分层

预分层发生在全文核验之前，用于控制高成本阅读规模。所有判断都要保留依据和不确定项。

#### 团队分层（T）

根据原文署名、机构官方页面和作者档案标记：

- T1：顶级模型公司核心研究团队、顶级科技公司 Research、顶尖大学或实验室、国家级 AI 安全与评测机构、领域核心研究者。
- T2：具有可靠专业地位、研究能力和一手性的团队或作者。
- T3：专业背书、一手性或研究贡献不足。

执行规则：

- T3 不进入正式全文核验队列。
- 公司品牌、职务头衔、融资规模或作者名气不能单独决定 T 级。
- 按实际参与本文研究或写作的主体定级。
- 团队身份不确定时，仅在出现强 P0/P1 信号时暂存为“待补证据”。
- 身份不确定项先补作者和机构证据，不直接投入全文阅读。

#### 议题分层（P）

根据标题、摘要、目录和必要关键段落标记：

- P0：Eval、Benchmark、Data、Judge、Harness、Agent 评测及评测基础设施。
- P1：Agent、Coding Agent、Computer Use、世界模型、具身智能、VLA、多模态推理等重点方向。
- P2：其他具有技术价值的 AI 议题。

不能仅因标题出现 Eval、Bench、Dataset 或 Agent 就升级；必须记录文章实际研究对象和技术问题。

### 3.4 第四层：价值预判与决赛圈

仅对 T1/T2 候选判断：

- 整数智能和 ZODA 读者是否可能感兴趣；
- 是否符合专业、证据导向的品牌调性；
- 是否存在方法、实验、数据或系统证据；
- 是否揭示数据、Evaluator、Judge、Harness、复现、成本或外推问题；
- 能否形成具体的数据与评测判断；
- 是否具有区别于一般中文编译的角度；
- 是否有助于最终维持至少 60% 的 Eval 强相关配比。

全文核验队列按以下顺序排列：

1. 团队达到 T1/T2 准入；
2. P0 优先于 P1，P1 优先于 P2；
3. 读者兴趣；
4. 品牌调性；
5. 技术证据潜力；
6. 差异化角度。

预分层不是最终定级。

### 3.5 第五层：全文核验与最终入选

只对进入决赛圈的候选投入高成本核验。

逐篇确认：

- 原始标题和规范化 URL；
- 精确发布日期；
- 正文完整性；
- 作者或机构身份；
- 研究问题和任务；
- 数据来源与构造方式；
- 方法和系统设计；
- 实验、对照和指标；
- Evaluator、Judge、Harness 和工具配置；
- 主要结果；
- 作者明确披露的限制；
- 不能从材料推出的结论。

必须严格区分：

- 作者或发布方自报；
- 第三方验证；
- 独立复现；
- 编辑判断和推断；
- 模型自身成绩；
- “模型 + Harness + Tools”的系统成绩。

作者与机构核验规则：

- 个人作者需核验最近可确认的工作经历和一个代表成果。
- 找不到可靠履历时写“公开履历未核实”，不得猜测。
- 机构署名文章只介绍机构，不虚构个人作者。
- 普通 arXiv 作者原则上只介绍论文中可确认的研究机构。

全文核验后复核 T/P：

- 作者贡献或机构身份不符时调整 T 级；
- 文章实质议题与预判不符时调整 P 级；
- 降为 T3 的候选立即退出；
- 不得为维持数量而保留不合格文章；
- 所有定级变化都要记录原因。

## 4. 传播验证与评分

### 4.1 传播验证

运行：

```bash
agent-reach doctor --json
node scripts/propagation-check.mjs \
  --title "原始标题" \
  --url "原文 URL" \
  --authors "作者或团队"
```

检查渠道：

- X；
- Hacker News；
- Newsletter；
- 专业研究者讨论。

传播信号只用于总分中的 10 分，不能代替技术判断。渠道不可用或证据不足时：

- 记录缺失渠道；
- 保守记 0 分；
- 不估算互动量；
- 不把 Hacker News 排名或点赞直接视为技术价值。

### 4.2 五维评分

总分 100 分：

- 业务与议题相关性：40 分；
- 技术增量或解释价值：25 分；
- 研究者或团队背景背书：20 分；
- 传播验证：10 分；
- 转载编译可行性：5 分。

等级划分：

- S：86–100；
- A：71–85；
- B：65–70；
- C：0–64。

高分不能抵消硬门槛、T/P 准入要求或红线。

### 4.3 Scorecard 校验

每条候选必须填写 `scorecard-template.json`，然后运行：

```bash
node scripts/validate-scorecard.mjs PATH_TO_SCORECARD.json
```

校验器必须确认：

- 五项分数齐全；
- 单项没有越界；
- 总分正确；
- 等级匹配；
- T/P 准入有效；
- 红线已经检查。

校验失败必须修复，不能以人工目测代替。

## 5. 编辑判断与结果组合

### 5.1 提炼数据与评测角度

每篇文章选择一个最合适的核心问题：

- Benchmark 测到的是模型能力，还是 Harness、Tools 和推理预算？
- 指标提升是否对应真实任务？
- Judge 的偏差、方差和校准是否足以支持结论？
- 数据设计改变了什么，还有哪些真实分布没有覆盖？
- 自动化评测减少了什么成本，又引入了什么盲区？
- 结果能否跨模型、任务、环境和成本预算外推？
- 失败模式是否比平均分更值得关注？
- 实际评估对象是否已从模型转向完整系统？

切入角度必须：

- 说明整数智能和 ZODA 为什么分享它；
- 落到数据、环境、轨迹、标注、验证或评分信号；
- 说明文章代表的数据或评测范式变化；
- 区分原文事实与编辑追问；
- 只在材料支持时关联 ZODA Benchmark、Leaderboard、Challenge、House 或专家生态。

不得：

- 把文章摘要换一种说法；
- 使用“值得关注”“深度解析”等空话；
- 机械罗列数据、评测、Benchmark 等标签；
- 强行设计原文没有支持的新数据集；
- 机械套用 ZODA 四个板块。

### 5.2 组合最终结果

最终结果必须：

- 交付 10–15 篇；不足时说明原因，不凑数；
- 至少包含 `ceil(结果数 × 0.6)` 篇 Eval 强相关文章；
- 只包含最终确认的 T1/T2；
- 控制主题、机构和重复度；
- 对重复推荐标注此前推荐日期；
- 每篇提供原始链接和精确发布时间。

## 6. 交付格式

不得使用 Markdown 表格、卡片、独立评分栏或总览摘要。每篇固定包含以下七个字段：

```text
N. 推荐选题：[中文选题标题]

选题理由：选题评级 [S/A/B/C] 级，整体评分 [X]/100，团队与议题组合为 [T1/T2]＋[P0/P1/P2]。评分依据：业务与议题相关性 [X]/40：[依据]；技术增量或解释价值 [X]/25：[依据]；研究者/研究团队背景背书 [X]/20：[依据]；传播验证 [X]/10：[依据]；转载编译可行性 [X]/5：[依据]。

整数智能 / ZODA 切入角度（数据/评测判断）：[完整自然段]

文章主要内容：
• 研究问题：[一句]
• 研究过程与方法创新：[一句]
• 研究结论：[一句，并说明属于作者报告]
• 意义与价值：[一句，并注明适用边界]

发布人/研究者简介：[已核验简介]

发布时间：[YYYY-MM-DD]

原文：[规范化完整 URL]
```

除“文章主要内容”的四项外，不使用项目符号。

## 7. 留痕与审计

### 7.1 推荐历史

交付成功后运行：

```bash
node scripts/recommendation-history.mjs record URL_1 URL_2 ...
```

只记录实际交付文章，不记录被淘汰候选。

### 7.2 漏斗台账

全过程记录以下五层数量：

1. 实际抓取成功的原始条目数 X；
2. URL 规范化和去重后的候选数 Y；
3. 通过团队 T/P 预分层的候选数 Z；
4. 通过读者兴趣、品牌调性和数据/评测价值预判的决赛圈数量 M；
5. 完成全文、数据来源、评分和差异化角度核验后的最终数量 N。

同步记录淘汰原因：

- 重复；
- 日期或正文不合格；
- T3 或团队证据不足；
- 议题匹配不足；
- 读者兴趣弱；
- 调性不符；
- 原文、作者或数据不可核验；
- 缺少差异化角度；
- 评分或红线未通过。

### 7.3 固定结尾

整份输出的最后一句必须是：

> 这轮我们通过定向搜索、抓取和 AI 提炼，共看了 X 篇原始内容，去重后得到 Y 篇候选；经团队与议题预分层剩 Z 篇，再按读者兴趣、调性及数据/评测相关性筛到 M 篇，最后核查全文、数据来源和差异化角度，留下 N 篇可用选题。

X/Y/Z/M/N 必须来自本轮真实台账；精确统计不写“约”，仅在存在可解释的区间统计时使用“约”或区间。N 必须等于实际交付数量。
